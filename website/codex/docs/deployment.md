# Deployment notes

The website is a public **server-rendered Next.js** application. `next build`
writes `website/.next`; no authentication service or login-related environment
configuration is required. Pages are prerendered where they can be, so most
content is fixed at build time even though requests are served by a Node runtime.

That has one consequence worth knowing before troubleshooting anything else:

> **A failed deployment is invisible on the site.** The alias keeps serving the
> last build that succeeded. There is no error page and no banner. Published
> content simply looks like it was reverted.

## Which build is live?

Open `/build.txt` on whichever URL you are looking at:

```
https://<host>/build.txt
```

It reports the commit, branch, environment, and build time. The same commit and
time are stamped into the `<head>` of every page:

```html
<meta name="build-commit" content="…" />
<meta name="build-time" content="…" />
```

`/build.txt` is generated by `scripts/write_build_stamp.mjs` during `prebuild`;
the meta tags come from `website/app/lib/buildInfo.ts`. Both read the commit from
`VERCEL_GIT_COMMIT_SHA`, and fall back to the local git HEAD outside a hosted
build. Neither file is committed — the stamp is build output.

If the commit in `/build.txt` is not the commit you expect, the content is not
the problem. The deployment that should have published it did not run, or did
not succeed.

## When the site does not reflect a merge

Check in this order.

1. **`/build.txt`.** If it names the merge commit, the build is live and the
   issue is a cached page in your browser — hard-reload. If it names an older
   commit, keep going.
2. **Was a production deployment created?** In the Vercel dashboard, the
   project's Deployments list should show one for the merge commit, marked
   Production. No entry means the Git integration never fired.
3. **Did it fail before building?** Configuration errors are rejected *before*
   the build runs, so the log will be a few lines long with no build output. See
   the `vercel.json` note below.
4. **Is the production branch right?** The project's Git settings name the branch
   that produces production deployments. It must be `main`.
5. **Is the alias pointing at the newest production deployment?** A deployment
   can succeed while the domain still resolves to an older one — the dashboard's
   Domains view shows what each alias is assigned to. Promoting the newest
   deployment reassigns it.

A local reproduction of exactly what the host runs:

```bash
git checkout main && git pull
rm -rf node_modules website/.next
npm install
npm --workspace website run build     # the buildCommand from vercel.json
```

If that succeeds and the deployment still does not, the failure is in the hosting
configuration rather than in the repository.

## `vercel.json`

The file carries the install and build commands, the output directory, and the
redirect for the sixth guide's former route. Two rules:

- **Vercel validates it against a closed schema and rejects unknown keys.** A
  redirect may carry only `source`, `destination`, `permanent`, `statusCode`,
  `has`, and `missing`. Anything else — including a `comment` field added to
  explain the entry — fails the deployment before the build starts. Because JSON
  has no comments, explanations belong in this file or alongside the check in
  `website/scripts-lint.mjs`, never in the JSON.
- **`npm run lint` parses it** and fails on an unsupported key, a redirect
  missing its source or destination, a redirect that is no longer permanent, or a
  changed destination for the old guide route. That turns a deploy-time rejection
  into a local failure.

## Redirects

Redirects for moved routes live in `vercel.json`, where `npm run lint` checks
them. `trailingSlash: true` means
both forms must be listed:

```json
{ "source": "/learn-ai/old-route",  "destination": "/learn-ai/new-route/", "permanent": true },
{ "source": "/learn-ai/old-route/", "destination": "/learn-ai/new-route/", "permanent": true }
```

`permanent: true` produces a **308**, which browsers and search engines cache
aggressively. That is correct for a route that has genuinely moved, but it means
a mistaken destination is expensive to undo — check the destination before
merging.
